# AirHouse — Stitch Design Upgrade: Execution Plan & Replit Master Prompt

**Source:** 35 screens from Google Stitch (PropTech Trust Systems design language)
**Target:** Existing AirHouse codebase (React 18 + Vite + Supabase + Express/Resend, live at airhouse.co.za)
**Strategy:** Parallel multi-agent execution with strict dependency gates

---

## 1. Stitch Design Audit (What I Found)

### 1.1 The "PropTech Trust Systems" design language

Stitch shipped a complete Material Design 3-flavoured token system. Locked-down identity:

- **Font:** Inter (single family across all weights 400/500/600/700) + Material Symbols Outlined for icons
- **Border radius philosophy:** *Soft but sharp* — `0.125rem` default (2px), `lg=0.25rem` (4px) for cards/buttons, `xl=0.5rem` (8px) for hero containers, `full=0.75rem` (12px) for max-rounded. **No pill shapes.** This is the opposite of consumer-app rounding.
- **Spacing scale (custom names):** `xs=4 / sm=12 / base=8 / md=24 / gutter=24 / margin=32 / lg=48 / xl=80` (px). All grid math is on an 8px base.
- **Layout grid:** Fixed 12-col, max container width **1280px**, sidebar **256px** (`lg:ml-64`).
- **Elevation:** No drop shadows. Uses `.ambient-shadow` = `0 4px 24px rgba(17,24,39,0.06)` only on raised cards/modals + 1px outlines (`outline-variant #c0c8c4`) for separation.

### 1.2 Color palette (exact hex)

Two parallel palettes are present in the files — the canonical M3 tokens (DESIGN.md) and a "marketing" pair (#6B9B8C sage + #6EE7B7 mint) used in the landing/dashboard chrome. **These must be reconciled.** The recommendation below uses the M3 token names because every screen references them.

| Token | Hex | Use |
|---|---|---|
| `primary` | `#38675a` | Headers, primary nav active state, brand text |
| `primary-container` | `#6b9b8c` | Sidebar logo block, secondary chrome |
| `secondary` | `#006c4e` | Success states, ZAR currency emphasis |
| `secondary-container` | `#80f9c8` | **Primary CTA buttons** (with `on-secondary-container` text `#007353`) |
| `secondary-fixed-dim` | `#62dcad` | CTA hover state |
| `surface` / `background` | `#f9f9ff` | Page background |
| `surface-container-lowest` | `#ffffff` | Card surfaces |
| `surface-container-low` | `#f1f3ff` | Sidebar background |
| `surface-variant` | `#dce2f7` | Subtle dividers, chip backgrounds |
| `outline-variant` | `#c0c8c4` | Card borders (1px), table dividers |
| `on-surface` | `#141b2b` | Primary text |
| `on-surface-variant` | `#404945` | Secondary/muted text |
| `error` / `error-container` | `#ba1a1a` / `#ffdad6` | Destructive, increased CPL |
| `tertiary` / `tertiary-container` | `#555f6d` / `#8892a2` | Disabled / placeholder content |

### 1.6 Critical reconciliation issues to flag

- **Dual color story** in Stitch HTML: the marketing pages use raw `#6B9B8C`/`#6EE7B7` while internal app pages use M3 token names. Pick **token names everywhere** and remove ad-hoc hex from JSX.
- **Sidebar inconsistency:** different Stitch screens show different nav item lists. We will define ONE canonical nav per role (see §3.3).
- **Stitch HTML uses Tailwind CDN.** The real app is Vite + Tailwind built. We need to migrate the config (colors/spacing/fonts), not ship the CDN.
- **Material Symbols** must be loaded once globally, not per page.

## 2. Execution Strategy: Parallel Agent Plan

Replit Agents work best when (a) tasks are surgically scoped, (b) shared dependencies are built first, and (c) each agent has clear file boundaries to avoid merge conflicts. The plan below uses **5 sequential phases**, with **multiple agents running in parallel inside each phase**.

### Phase 0 — Pre-flight (single agent, blocking, ~15 min)

Setup foundations all other agents depend on. Cannot be parallelized.

**Tasks:**
1. Create branch `feat/stitch-design-system`.
2. Update `tailwind.config.js` with the full PropTech token set (colors, spacing, fontSize, borderRadius, fontFamily).
3. Add `Inter` + `Material Symbols Outlined` to `index.html` `<head>`.
4. Create `src/styles/tokens.css` with the `.ambient-shadow` utility.
5. Create `src/components/_design-system/` folder with primitives: `Button`, `Card`, `Chip`, `MetricCard`, `Sidebar`, `TopAppBar`, `PageHeader`, `EmptyState`, `Skeleton`.
6. Create a Storybook-less "kitchen sink" page at `/_design-preview` (dev only) that renders every primitive — used as a smoke test.
7. Commit. **Gate before Phase 1.**

### Phase 1 — Shared shells & global UI (3 agents in parallel)

**Agent 1A — App Shell (sidebar + top app bar)**
- Build `<RoleSidebar role="developer|creator|admin" />` with the canonical nav per role.
- Build `<TopAppBar />` with search input, notifications bell, help icon, profile avatar.
- Wire to React Router's active route detection (use `NavLink`).
- Mobile: existing slide-in drawer behavior preserved; just restyle.

**Agent 1B — Notifications + Messages**
- Restyle `notifications_panel` (in-app dropdown that already exists, just retheme + use Material Symbols).
- Build `messages` page using the Stitch two-pane layout (thread list left, conversation right). If real-time messaging isn't already wired, scaffold the Supabase table `messages (sender_id, recipient_id, body, campaign_id, created_at, read_at)` + RLS + a simple polling read every 15s.

**Agent 1C — Auth/Landing/Onboarding**
- Restyle `landing_page` with the bento hero + testimonials.
- Restyle 3-step onboarding wizards for both roles (already exists — apply tokens, copy the exact form-field structure from Stitch HTML).
- Restyle login/signup pages to match landing aesthetic.

### Phase 2 — Role dashboards & analytics (4 agents in parallel)

**Agent 2A — Developer Dashboard + ROI**
- `developer_dashboard`: 4 KPI cards + lead pipeline summary chart + recent campaigns table.
- `developer_roi_dashboard`: per-campaign profitability with revenue minus cost (read existing analytics computations; do not change calculation logic).

**Agent 2B — Creator Dashboard + Scorecard + Public Profile**
- `creator_dashboard`: earnings card + active campaigns + tracking links table.
- `creator_performance_scorecard_refined`: tier (Bronze/Silver/Gold/Platinum) computed from existing reliability/approval/on-time fields. Visual: 3 metric arcs/bars + tier card.
- `public_profile`: refresh the existing `/creators/:id` page to match the Stitch design (avatar, bio, stats, specialties, past campaigns, reviews).
- `social_proof_badges`: gallery view of existing achievements (read from existing achievements table — do not add new ones).

**Agent 2C — Super Admin Dashboard + Verification Review + Analytics**
- `super_admin_dashboard`: Platform revenue / 25% commission earned / active campaigns / verified creators count, plus Active Disputes table and Verification Queue. **Restrict route to `ashleybaloyi.work@gmail.com` via existing role check.**
- `admin_verification_review`: side-by-side ID + selfie + decision panel.
- `admin_analytics_dashboard`: macro charts (revenue trend, top regions, top creator categories).

**Agent 2D — Sales Pipeline + Lead Detail**
- `sales_pipeline`: kanban with the 5 columns (New / Contacted / Qualified / Converted / Lost). Use HTML5 drag-and-drop (existing functionality presumably exists; just restyle and ensure column drops update `lead.status`).
- New Lead Detail modal/page with conversation history, source attribution, UTM data.

### Phase 3 — New features (gap fillers, 4 agents in parallel)

**Agent 3A — Property Listing Manager (NEW)**
- DB: create `properties` table → `id, developer_id (FK profiles), title, slug, description, price_zar (numeric), location_city, location_suburb, latitude, longitude, bedrooms, bathrooms, parking, floor_area_sqm, status (enum: draft, active, sold, archived), photo_urls (text[]), created_at, updated_at`. RLS: developer can CRUD own; creators read-only on `status='active'`; admin all-access.
- Backend: storage bucket `property-photos` with RLS.
- UI: list view with filters + grid/list toggle (Stitch shows both), single property edit form, photo upload with reordering, link a property to a campaign.
- Wire campaigns to `property_id` (add column if missing).

**Agent 3B — Creator Marketplace (NEW)**
- Page: `/marketplace` — searchable, filterable directory of creators. Filters: niche (multi-select), follower range, price range (ZAR), location, verification status.
- Cards link to existing `/creators/:id`.
- Server-side search via Supabase `ilike` on `creator_profiles.bio + display_name + skills`. Use existing `creator_profiles` table.

**Agent 3C — Disputes + Digital Contracts UI**
- Dispute reporting from any campaign assignment (button: "Report Issue" → modal with reason category + description + evidence upload to Supabase storage).
- `admin_dispute_mediation`: queue of open cases left, thread + actions panel right (release escrow / refund / escalate). Hook to existing `disputes` table.
- `digital_contract`: read-only view of agreed terms + dual-signature blocks. Generate signed timestamps when a creator accepts an assignment.

**Agent 3D — Invoices, Ledger, Payouts**
- `transaction_invoice_detail`: per-payment view with line items showing gross, 25% platform fee, 3% creator payout fee, net to creator. Export to PDF using `@react-pdf/renderer` (client-side; no extra service).
- `financial_ledger_transactions`: full table of transactions with date filter, status filter, CSV export.
- `payouts`: restyle existing payout request flow + add escrow status indicator.

### Phase 4 — Workflow polish (2 agents in parallel)

**Agent 4A — Campaign + Assignment flow refinements**
- `campaign_manager`: brief editor with rich text (existing field, just restyle), budget input with ZAR formatting, target audience tags.
- `assignments_overview`: filterable list view of all assignments with status pills.
- `assignment_detail_acceptance`: full brief preview + accept/decline buttons + auto-generates digital contract on accept.
- `content_submission`: form for creator to submit deliverable URLs + tracking link + notes; triggers existing email notification to developer.
- `id_verification_upload` + `verification_status_overview`: surface progress through email-verified → ID-verified → social-proof-verified.

**Agent 4B — Help & Support + Empty states + Loading states**
- `help_support_center`: searchable FAQ + contact admin form. Articles can be hard-coded markdown in `src/content/help/` initially.
- Empty states for every list view (no campaigns, no leads, no creators, no notifications) using consistent illustration + CTA pattern.
- Skeleton loaders for every page that fetches from Supabase.
- 404 + 403 pages restyled.
- Toast styling pass via `react-hot-toast` config.

### Phase 5 — QA, accessibility, ship (single agent)

- Manual route walkthrough using a checklist (see §6).
- Lighthouse run on top 5 routes.
- A11y: keyboard tab order on all forms, `aria-label` on icon-only buttons, color contrast (M3 tokens already pass).
- Responsive sweep at 375 / 768 / 1280 / 1920.
- Smoke test against production-like data.
- Merge to `main`, deploy.

### Why this order

Phase 0 unblocks every visual decision. Phase 1 builds the chrome that Phase 2 dashboards plug into. Phase 3 introduces the *new* features that Phase 4 then refines. Each phase has a clean dependency on prior outputs, but **within a phase, agents touch disjoint folders**, so they can run truly in parallel without conflict.

## 4. Database migrations needed

### 4.1 New tables

```sql
-- Properties (Phase 3A)
create table public.properties (
  id uuid primary key default gen_random_uuid(),
  developer_id uuid not null references public.profiles(id) on delete cascade,
  title text not null,
  slug text not null unique,
  description text,
  price_zar numeric(14,2) not null,
  location_city text,
  location_suburb text,
  latitude numeric(9,6),
  longitude numeric(9,6),
  bedrooms int,
  bathrooms int,
  parking int,
  floor_area_sqm int,
  status text not null default 'draft' check (status in ('draft','active','sold','archived')),
  photo_urls text[] default '{}',
  created_at timestamptz default now(),
  updated_at timestamptz default now()
);

alter table public.properties enable row level security;
create policy "developers manage own properties" on public.properties
  for all using (auth.uid() = developer_id) with check (auth.uid() = developer_id);
create policy "anyone reads active properties" on public.properties
  for select using (status = 'active');
create policy "admins all access properties" on public.properties
  for all using (exists (select 1 from public.profiles p where p.id = auth.uid() and p.role = 'admin'));

-- Messages (Phase 1B, if not already present)
create table if not exists public.messages (
  id uuid primary key default gen_random_uuid(),
  sender_id uuid not null references public.profiles(id) on delete cascade,
  recipient_id uuid not null references public.profiles(id) on delete cascade,
  campaign_id uuid references public.campaigns(id) on delete set null,
  body text not null,
  created_at timestamptz default now(),
  read_at timestamptz
);

alter table public.messages enable row level security;
create policy "participants read messages" on public.messages
  for select using (auth.uid() = sender_id or auth.uid() = recipient_id);
create policy "sender writes messages" on public.messages
  for insert with check (auth.uid() = sender_id);
create policy "recipient marks read" on public.messages
  for update using (auth.uid() = recipient_id) with check (auth.uid() = recipient_id);
```

```sql
  add column if not exists property_id uuid references public.properties(id) on delete set null;

alter table public.contracts

  add column if not exists developer_signed_at timestamptz;
```

### 4.3 Storage buckets

```sql
-- Run in Supabase dashboard
insert into storage.buckets (id, name, public)

  on storage.objects for insert
  with check (bucket_id = 'property-photos' and auth.uid()::text = (storage.foldername(name))[1]);

create policy "anyone reads property photos"
  on storage.objects for select using (bucket_id = 'property-photos');
```

## 7. Risk register

| Risk | Mitigation |
|---|---|
| Tailwind config conflicts between Stitch tokens and existing brand | Phase 0 commits the merged config; every later agent reads from it. |
| Two agents editing `App.jsx` routing | Phase 0 establishes the full routing map; later agents only add lazy imports. |
| Supabase migration drift | All Phase 3 migrations combined into one file before apply. |
| Visual drift between phases | `/_design-preview` route is the canonical reference; agents diff against it. |
| Production downtime during deploy | Deploy from `feat/stitch-design-system` to a preview URL first; cut over only after Phase 5 sign-off. |
| Stitch HTML referenced raw hex colors | Phase 0 gates: "no raw hex in JSX" lint rule (or grep in CI). |

## 8. What I'd do differently if you have time

- **Add Storybook** during Phase 0 instead of `/_design-preview`. Three days of investment pays back across all phases.
- **Add Playwright smoke tests** for the 8 most critical user journeys before Phase 5 — catches regressions the agents introduce.
- **Add an `app_settings` table** with the 25%/3% fee constants so they're configurable without redeploys (good prep for future).
- Replace 30s notification polling with **Supabase Realtime** subscriptions when you have a free moment — it's a one-file change but better UX.
